
Alright, I read the orchestrator, planner, router, every agent, the LLM client, the MCP registry in app.py, and ran a couple of live queries to see what actually happens. Here's my honest take — the
short version is: the plumbing is solid, but the code does not currently demonstrate multi-agent collaboration. It demonstrates routing to one stub. The README.md in the repo already diagnoses most of
this (and you should trust it — I re-verified most of those findings below).

What works well

  • LibreChat integration is clean. The OpenAI-compatible shim in src/app.py (/v1/chat/completions + /v1/models) is the right way to expose a custom backend to LibreChat. No adapters needed.
  • LangGraph is a fine framework choice for this problem, and you've set up a reasonable StateGraph with explicit nodes (planner → prepare_data → route → execute → next) and conditional edges.
  • Planner is structured. Using Pydantic + NVIDIA NIM guided_json to force a Plan { goal, rationale, steps[] } is the right instinct — it's what gives you an auditable, replayable plan instead of a
  freeform blob.
  • Separation of concerns is roughly right: planner decides what, router decides who, agents do the work, llm_client is the one point of LLM contact, data_loader isolates I/O. That's a good skeleton
  to iterate on.
  • Dockerised and reproducible. The override compose file and the health check are production-minded.

What's actually broken (the demo-killers)

I ran two different queries against the live service and watched the logs. Both queries returned:

"This is a placeholder response from General Advisor agent."

…and the logs show why. There are three cascading bugs, each of which would independently sink a MAS demo:

1. The planner never produces a usable plan

Live log from docker logs finai-api:

[ERROR from planner.py]: Failed to parse plan: Expecting value: line 1 column 1 (char 0)
[DEBUG from planner.py]: Raw text: To address the user's goal … **Step 1:** **Agent:** `digital_twin_persona` …
[DEBUG from planner.py]: Using fallback plan with 1 steps

The LLM (nvidia/llama-3.3-nemotron-super-49b-v1.5) is returning markdown prose, not JSON — so guided_json is not taking effect. Every single request falls through to the hard-coded fallback plan,
which is always general_advisor, 1 step. The "planner" layer is decorative right now.

Most likely cause: NVIDIA NIM doesn't honour vLLM's extra_body={"guided_json": ...} the same way. For NIM you typically need either response_format={"type": "json_object"} or nvext={"guided_json": 
schema}, plus a strong "output JSON only, no prose" instruction.

2. The agents are stubs

Every agent file (upstox.py, digital_twin.py, deep_web_research.py, us_stock.py, indian_stock.py, general_advisor.py) ignores its inputs and does:

return "This is a placeholder response from X agent."

No LLM call, no specialisation, no tool use. The tools/Upstox-MCP-Server (a full TypeScript MCP server), tools/DeepWebResearch/main.py, tools/DigitalPersona/main.py are all present in the repo but no 
agent imports them. So there is no multi-agent system yet — there are six classes that happen to have different names and the same body.

3. The router is dead code and would crash if reached

src/core/router.py maps regex intents to keys like fin_score, credits_loans, investment_coach, insurance_analyzer, retirement_planner, tax_planner, fraud_shield, fin_advisor. None of those exist in 
the registry in orchestrator.py:

registry = {"upstox", "digital_twin_persona", "deep_web_research",
            "us_stock_analysis", "indian_stock_analysis", "general_advisor"}

And the router is only invoked when a plan step has agent == "router", which the planner prompt never requests. So it's orphaned — but worse, if it ever did fire, _resolve_agent() would KeyError every
time.

4. Even if plans had multiple steps, collaboration wouldn't happen

_node_execute (orchestrator.py:186) does:

new["result"] = payload

Each step's output overwrites the previous one. No list, no shared scratchpad getting read, no aggregator. So there is structurally no way for agent B to see agent A's output, and no place for a
synthesiser to combine them. This is the single biggest architectural issue for your stated goal.

5. Small but telling bugs

  • orchestrator.py:128: hinted = state.get("fin_advisor") — should be "hinted_agent".
  • app.py:86: regex r"\b(Indian|Stock|)\b" has an empty alternative → matches almost anything.
  • /agent/{agent_name} (app.py:124) returns "Simulated response from ..." — it doesn't call any agent.
  • chat_completions rebuilds the whole Orchestrator (and LLMClient) per request.
  • stream=true is faked: the whole response is computed synchronously, then emitted as a single chunk + [DONE]. No actual token streaming.
  • Three different agent-key registries in app.py, agents/__all_minimal__.py, and core/planner.py — subtly inconsistent (us_stock vs us_stock_analysis, etc.).
  • .env is committed with a real OPENAI_API_KEY and NVIDIA_API_KEY. Rotate those and add to .gitignore. This is the most time-sensitive thing in this review.

My honest verdict on "shows how a multi-agent system collaborates"

Right now it doesn't — and anyone who looks past the nice Plan schema or the LibreChat UI will notice. Because the planner silently falls back, every query goes through the exact same path
(general_advisor placeholder), and the architecture can't aggregate multiple agents even if the planner did produce a multi-step plan. The crew-style code that would have done synthesis is commented
out in _node_execute lines 149–168.

To put it in a presentable shape, the minimum I'd do is roughly:

  • Fix structured output. Either (a) switch to NVIDIA NIM's response_format={"type":"json_object"} + stronger system prompt, or (b) wrap the call in instructor/pydantic-ai, or (c) fallback to regex-
  extracting the first {...} block before erroring. You'll instantly get multi-step plans.
  • Make agents real and distinct. Each run() should call LLMClient.get_chat_model with a different system prompt and — for the demo wow-factor — one tool each: Upstox hits a stubbed portfolio JSON,
  DeepWebResearch hits DuckDuckGo or a cached snippet, USStock calls yfinance, etc. Two real ones are more impressive than six fake ones.
  • Collect outputs, don't overwrite. Change state["result"] → state["results"]: List[Dict]. Each execute-node appends.
  • Add a synthesizer node after the loop. It takes the full results list + original query and asks the LLM to write the final user-facing answer. This is the collaboration people will see.
  • Fan out in parallel for independent agents. LangGraph's Send API is made for this — it would visibly demonstrate parallel MAS, which is the thing the audience actually wants to see.
  • Delete the router (the planner already picks agents) or align its keys and re-wire it as a pre-planner intent classifier. Right now it confuses the architecture story more than it helps.
  • Unify the agent registry into a single source of truth (one module that app.py, planner.py, orchestrator.py all import).
  • Rotate & gitignore the API keys.

TL;DR

  • As a LibreChat + LangGraph integration template: B+. Clean, working, reproducible.
  • As a multi-agent collaboration demo: D. One silently-broken planner, six identical stubs, dead router, no aggregation. The README itself already says most of this — I just verified it's still
  true.

The good news: items 1–4 above are probably a weekend of work, and they would turn this from "single-agent-with-extra-steps" into a genuinely compelling MAS demo without you having to change the
framework or the LibreChat setup. Want me to take a first pass at any of them — I'd suggest starting with #1 (fix the planner's JSON output) since it unblocks everything else?
